# 08. 대용량 트래픽 처리 / 분산 처리

공고 인용: "대용량 트래픽 최적화하고 분산 처리 구현 경험이 있으신 분", 팀 소개 "대규모 트래픽을 안정적으로 처리하며, 글로벌 서비스의 성장을 뒷받침하는 핵심 시스템을 만듭니다."

## 1. 트래픽 문제를 구조적으로 쪼개서 생각하기

인터뷰에서 "대용량 트래픽 처리 경험 있나요?"에 막연히 답하지 않도록, 항상 **어디가 병목인지(CPU/메모리/네트워크/DB)부터 짚고 대응책을 매칭**하는 순서로 답변을 구성한다.

```
클라이언트 → (CDN/캐시) → 로드밸런서 → WAS(수평 확장) → (캐시) → DB(읽기 복제본, 샤딩)
```

## 2. 수평 확장(Scale-out) vs 수직 확장(Scale-up)

| | 수직 확장 | 수평 확장 |
|---|---|---|
| 방법 | 서버 스펙 증설(CPU/RAM) | 서버 대수 증설 |
| 한계 | 물리적 상한 존재, 단일 장애점 | 이론상 무한 확장 가능 |
| 전제조건 | 없음 | **애플리케이션이 stateless여야 함** |

- Spring Bean이 기본 stateless(01번 문서)여야 하는 이유가 바로 여기 — 서버 인스턴스가 여러 대일 때 특정 요청이 어느 서버로 가도 같은 결과가 나와야 함. 세션 같은 상태는 서버 로컬 메모리가 아니라 **Redis 같은 외부 저장소에 분리**(session externalization)해야 수평 확장이 가능해짐.

## 3. 캐싱 전략 — 계층별로 정리

```
브라우저 캐시 → CDN(정적 자원, 지리적으로 가까운 엣지 서버) → 애플리케이션 캐시(Redis, 05번 문서) → DB 쿼리 캐시
```
- 요청이 원본 서버(origin)까지 가지 않고 앞단에서 처리될수록 지연/부하가 줄어듦 — "가능한 한 앞에서 막는다"는 원칙.
- 글로벌 서비스(공고에 "글로벌 사용자들을 위한 서비스 최적화" 명시) 맥락에서 CDN이 특히 중요 — 물리적 거리에 따른 네트워크 지연(latency)을 CDN 엣지 서버로 줄임.

## 4. 데이터베이스 확장 — Read Replica / Sharding

### 읽기 복제본(Read Replica)

- 읽기 트래픽이 압도적으로 많은 서비스(대부분의 웹 서비스)에서 **쓰기는 마스터, 읽기는 여러 복제본으로 분산**.
- 트레이드오프: **복제 지연(Replication Lag)** — 마스터에 쓴 직후 복제본에서 바로 읽으면 최신 데이터가 안 보일 수 있음(06번 문서의 최종 일관성과 같은 맥락). "방금 작성한 내 글이 잠깐 안 보이는" 현상의 원인.
- 완화책: 쓰기 직후 조회는 마스터에서 읽도록 라우팅(read-your-writes), 또는 사용자에게 낙관적 UI로 즉시 반영된 것처럼 보여줌.

### 샤딩(Sharding, 파티셔닝)

- 하나의 테이블/DB가 감당 못 할 정도로 커지면 **데이터를 여러 DB로 물리적으로 분산**. 기준(shard key) 선택이 핵심 — DynamoDB 파티션 키 설계(05번 문서)와 동일한 고민.
- 잘못된 shard key 예: 시간순 증가하는 값(예: auto-increment ID)을 그대로 쓰면 최신 데이터에 쓰기가 몰려 특정 샤드만 hot해짐 — 사용자 ID 해시처럼 고르게 분산되는 키를 선택해야 함.
- 샤딩 후엔 여러 샤드에 걸친 JOIN/트랜잭션이 불가능해짐 — MSA에서 서비스별 DB를 분리하는 것과 같은 종류의 트레이드오프.

## 5. 비동기 처리 — 메시지 큐로 부하 흡수

```
사용자 요청(이미지 업로드) → API 서버는 큐에 작업만 넣고 즉시 응답
  → Worker가 큐에서 꺼내 실제 이미지 처리(리사이즈, 썸네일 생성) 비동기 수행
```
- **즉시 응답이 필요 없는 무거운 작업**(이미지/영상 처리, 이메일 발송, 통계 집계)을 동기 요청 경로에서 빼내는 것 — API 서버가 무거운 작업에 스레드를 오래 붙잡지 않아 처리량(throughput)이 올라감.
- 큐가 트래픽 급증(spike)을 흡수하는 버퍼 역할도 함 — 순간적으로 요청이 몰려도 Worker가 자기 페이스대로 처리(back-pressure 개념, 09번 문서 Reactive와 연결).

## 6. Rate Limiting / 서킷 브레이커 — 과부하 방어

- **Rate Limiting**: 특정 사용자/IP가 짧은 시간에 과도한 요청을 보내면 차단 — Token Bucket, Leaky Bucket 알고리즘이 대표적 (Redis `INCR` + TTL로 간단히 구현 가능).
- **Circuit Breaker**(06번 문서 언급): 의존하는 서비스가 계속 실패하면 아예 호출을 끊고 즉시 실패 응답(fail-fast) — 실패할 요청에 스레드/시간을 낭비하지 않고, 장애가 전파(cascading failure)되는 것을 막음.

## 7. 성능 측정 없이 최적화하지 않는다

- "어디가 느린지 먼저 측정 → 가설 세우기 → 개선 → 재측정"이 원칙. 공고 기술스택에 Datadog/CloudWatch가 명시된 이유 — **모니터링 없이는 "체감상 느린 것 같다"는 추측 최적화**가 되기 쉬움.
- 흔히 보는 지표: p50/p95/p99 응답 지연(평균만 보면 소수의 매우 느린 요청을 놓침), 초당 요청 수(RPS/QPS), 에러율, 스레드 풀 사용률/큐 대기 시간.

## 8. 자주 나오는 질문

- "트래픽이 갑자기 10배 늘면 어떻게 대응하나요?" → 병목 지점 특정(캐시/DB/서버) 순서로 답변, 캐싱 계층 확장 → 서버 수평 확장 → DB 읽기 복제본 순으로 단계적 접근
- "DB가 병목인데 어떻게 하나요?" → 인덱스 최적화(04번) → 읽기 복제본 → 캐싱 → (그래도 안 되면) 샤딩
- "실시간 편집 기능이 트래픽 몰리면?" → WebSocket 서버 수평 확장 + Redis Pub/Sub(07번 문서와 연결)
- "측정 없이 최적화한 경험이 있나요?"류 질문 → 오히려 "측정부터 했다"는 사례로 반박하는 방향이 좋은 답변

## 실습 방법

1. `project/` API에 부하 테스트 도구(예: k6, JMeter 중 가벼운 것 하나)로 간단히 RPS 측정해보기
2. 캐시 적용 전/후 응답시간 비교 측정 (05번 문서 캐싱 실습과 연계)
3. Redis `INCR` + TTL로 초간단 Rate Limiter 직접 구현해보기
