# 06. 모놀리식 → MSA 전환 설계

공고 인용 주요업무: "MSA 전환 과정에 참여하여, 기존 모놀리식 아키텍처를 마이크로서비스로 분리하는 경험을 쌓고, 서비스 확장성과 유지보수성을 높이는 설계를 주도합니다."

## 1. 왜 모놀리식에서 시작해서 MSA로 가는가

- 지원 대상 서비스는 이미 서비스 중인 대형 서비스 — "처음부터 MSA"가 아니라 **잘 굴러가는 모놀리식을 언제/어떻게 쪼갤지**가 실제 과제. 이 관점이 인터뷰 답변의 기본 톤이어야 함 (신규 프로젝트라면 굳이 MSA로 시작할 이유가 약함 — 초기엔 오히려 오버엔지니어링).
- 모놀리식의 한계가 드러나는 신호: 배포마다 전체 서비스 영향, 특정 도메인(예: 결제)만 트래픽이 튀는데 전체를 스케일 아웃해야 함, 팀이 커지며 코드 충돌/빌드 시간 증가.

## 2. 어떻게 쪼갤 것인가 — 도메인 경계 찾기

### Bounded Context (DDD 개념)

- "회원", "결제", "검색"처럼 **공고에 명시된 핵심 도메인**이 서비스 분리의 후보 단위. 기준: **같이 자주 변경되는 것은 같은 서비스, 독립적으로 변경/배포되어야 하는 것은 다른 서비스**.
- 잘못된 분리 예: 테이블 단위로 기계적으로 쪼개기(예: `users` 테이블 서비스, `orders` 테이블 서비스) — 실제 비즈니스 트랜잭션이 여러 서비스에 걸쳐 매번 분산 트랜잭션을 필요로 하게 됨. **비즈니스 유스케이스 단위**로 경계를 잡아야 함.

### 서비스별 독립 DB 원칙

```
seller-service → seller DB
product-service → product DB
order-service   → order DB
payment-service → payment DB
```
(전형적인 커머스 도메인 분리 예시 — 서비스별 DB 소유 원칙을 보여주기 위한 것)

- **서비스 간 DB를 직접 공유하지 않는다** — 다른 서비스의 스키마 변경이 내 서비스를 깨뜨리면 안 되기 때문. 필요한 데이터는 API 호출이나 이벤트로 전달받아 자기 DB에 필요한 만큼 복제(비정규화)해서 저장.

## 3. 서비스 간 통신 — 동기 vs 비동기

### 동기 (REST/gRPC)

- 즉시 응답이 필요한 경우(예: 주문 생성 시 재고 확인). 단점: **호출받는 서비스가 느려지거나 죽으면 호출한 서비스까지 영향**(연쇄 장애) — Circuit Breaker(Resilience4j 등)로 완화.

### 비동기 (메시지 큐/이벤트, Kafka 등)

```
주문 서비스: "order.created" 이벤트 발행
  → 결제 서비스: 구독 후 결제 처리 → "payment.completed" 또는 "payment.failed" 발행
  → 주문 서비스: 구독 후 주문 상태를 PAID/CANCELLED로 변경
```
- **Choreography(안무형) Saga**: 중앙 조정자 없이 각 서비스가 이벤트를 구독/발행하며 흐름을 이어감 (위 실습 프로젝트 구조). 장점: 서비스 간 결합도 낮음. 단점: 전체 흐름을 한눈에 파악하기 어려움(트레이싱 필요).
- **Orchestration(오케스트레이션형) Saga**: 중앙 오케스트레이터가 각 단계를 순서대로 호출/보상. 장점: 흐름이 명확. 단점: 오케스트레이터가 단일 장애점이자 결합점이 되기 쉬움.
- "언제 동기, 언제 비동기?" → 호출 즉시 결과가 필요하고 강한 일관성이 필요하면 동기, 최종 일관성(eventual consistency)으로 충분하고 느슨한 결합이 중요하면 비동기.

## 4. 분산 트랜잭션 — Saga 패턴과 보상 트랜잭션

- MSA에서는 2PC(Two-Phase Commit) 같은 전통적 분산 트랜잭션을 잘 안 씀(가용성 희생이 큼). 대신 **각 단계를 독립 트랜잭션으로 처리하고, 실패 시 이전 단계를 되돌리는 보상(compensating) 트랜잭션**을 둔다.

```
1. 주문 생성 (성공)
2. 재고 차감 (성공)
3. 결제 처리 (실패!)
  → 보상: 재고 복구, 주문 취소로 상태 변경
```
- "왜 롤백이 아니라 보상인가" — 이미 다른 서비스 DB에 커밋된 트랜잭션은 되돌릴 수 없으므로(각자 독립 DB), 반대 방향의 새로운 트랜잭션(재고 복구)으로 상쇄시킴.

## 5. 데이터 일관성 — 최종 일관성(Eventual Consistency)

- MSA 환경에서는 "지금 이 순간 모든 서비스가 같은 상태를 본다"(강한 일관성)를 포기하고, "결국엔 같아진다"는 최종 일관성을 받아들이는 경우가 많음.
- 실무 함의: 주문을 막 생성한 직후 잠깐은 결제 상태가 "처리 중"으로 보일 수 있음 — 프론트엔드/사용자 경험 설계에도 영향을 준다는 걸 언급하면 실무 감각이 드러남.

## 6. 실시간 저장/동시 편집과 MSA — 이 공고만의 특수 포인트

- "실시간 저장 및 동시 편집 기능"은 일반적인 CRUD MSA보다 **상태 동기화 요구가 훨씬 높은** 도메인 — document 서비스가 독립적이더라도, 동시 편집 세션 상태(누가 지금 편집 중인지, 어떤 변경사항이 아직 다른 클라이언트에 전파 안 됐는지)는 Redis 같은 공유 저장소나 WebSocket 서버의 상태 관리가 별도로 필요함 (05, 07번 문서와 연결).

## 7. 자주 나오는 질문

- "모놀리식을 MSA로 어떻게 나누시겠어요?" → Bounded Context 기준 + 잘못된 분리 예시 언급
- "서비스 간 데이터 정합성은 어떻게 맞추나요?" → Saga + 보상 트랜잭션 + 최종 일관성
- "동기 호출이 실패하면?" → 타임아웃, 재시도, Circuit Breaker, fallback
- "MSA 전환의 단점은?" → 운영 복잡도 증가(분산 트레이싱, 배포 파이프라인 여러 개), 네트워크 지연/장애 지점 증가 — "장점만 말하지 않는 것"이 균형 잡힌 답변으로 평가받음

## 실습 방법

1. 위 seller/product/order/payment 예시로 서비스 간 이벤트 흐름을 직접 그림으로 그려보고 설명 연습 (03번 문서 멱등키를 payment 단계에, 04번 문서 재고 락을 product 단계에 적용해보면 전체 그림이 이어짐)
2. "지원 대상 서비스라면 어떤 도메인으로 나눌까"를 직접 설계해보기 (member, document, search, payment 후보로 Bounded Context 그려보기)
3. Saga 실패 시나리오(결제 실패) 하나를 골라 보상 트랜잭션 순서를 직접 써보기

## 참고 키워드 (검색용)

- Saga pattern choreography vs orchestration
- compensating transaction distributed systems
- eventual consistency vs strong consistency
